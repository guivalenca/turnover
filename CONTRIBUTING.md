# Contributing to Turnover

Thanks for helping. This page covers building, testing and changing Turnover. [docs/architecture.md](docs/architecture.md) explains how the parts fit together; read it before a larger change.

## Getting set up

You need macOS 15 or later and Xcode 26 or later. [XcodeGen](https://github.com/yonaskolb/XcodeGen) is needed only to change the Xcode project (`brew install xcodegen`).

```sh
git clone https://github.com/guivalenca/turnover.git
cd turnover
make test       # every test
make install    # build, sign and install the app, as in the README
```

| Command | What it does |
| --- | --- |
| `make install` | Build, sign, install to `/Applications`, turn on the Finder extension and launch |
| `make uninstall` | Quit, turn off and unregister everything `make install` set up, and reset permissions |
| `make app` | Build and sign `build/Turnover.app` only (`make install` removes it again) |
| `make test` | Run every test: TurnoverKit, the app core, the ring model and the command line |
| `make project` | Regenerate `Turnover.xcodeproj` from `project.yml` |
| `make clean` | Delete the build folders |

## Where things are

| Folder | What |
| --- | --- |
| `Sources/TurnoverKit` | Inspection, offers and estimates, conversion actions, output placement, the batch runner. The Finder extension, the app and the command all use it |
| `Sources/TurnoverAppCore` | The app's own rules, kept testable and out of the extension: launch, settings, Open at login, the menu bar item's timing, the notifications, and where new files go |
| `Sources/RingModel` | The ring's behaviour as a state machine, without AppKit |
| `Sources/TurnoverCLI` | The `turnover` command |
| `App` | Turnover.app: the background agent, the ring's windows, the menu bar item and the window |
| `FinderExtension` | The Finder Sync extension behind the right-click menu |
| `Tests` | Swift Testing suites, and small committed fixtures in `Tests/TurnoverTestSupport/Fixtures` |
| `scripts` | The generators for the icon and the test fixtures |
| `docs` | The architecture notes and the README's images |

## Tests

`make test` runs every suite, and CI runs them on every push, on macOS 26 with Xcode 26.6. CI also builds the app and checks that the committed Xcode project matches `project.yml`.

- Before Swift 6.4 (Xcode 27), a plain `swift test` uses SwiftPM's older build system, which doesn't compile the String Catalogs, and the plural tests fail. Run `make test`, or `swift test --build-system swiftbuild`.
- The timing tests (`EstimateTests`, `RefinementTests`, `MP4PlanTests`) can fail on a heavily loaded Mac. Run them again on a quiet one before suspecting a change.
- TurnoverKit's tests convert the real files in `Tests/TurnoverTestSupport/Fixtures`. `scripts/make-fixtures.sh` regenerates them; see the README in that folder.
- Automated tests can't drive Finder, the ring, a browser or the system prompts. The manual checklist in [the pull request template](.github/pull_request_template.md) covers them; go through the parts your change touches.

## The Xcode project

`Turnover.xcodeproj` is generated by XcodeGen from `project.yml`, and committed so that building needs only Xcode.

- After you edit `project.yml`, or add, move or remove a file under `App/` or `FinderExtension/`, run `make project`. CI fails if the committed project doesn't match.
- Changes made in Xcode's project editor are lost at the next `make project`. Make them in `project.yml`.
- `App/Info.plist` is generated too: add keys under `info.properties` in `project.yml`.
- Running the app from Xcode registers a second copy of it and its Finder extension. Run `make install` afterwards so that only the installed copy answers.

## Signing

`make app` signs with the first Apple Development certificate in your keychain, or ad hoc without one. macOS keys the permissions you grant to the signature, so a certificate keeps them across builds. To choose, pass `SIGN_IDENTITY`:

```sh
make install SIGN_IDENTITY="Apple Development: …"   # a certificate, by name or SHA-1
make install SIGN_IDENTITY=-                         # ad hoc
```

## Logs

Everything Turnover logs is under the `com.guivalenca.turnover` subsystem, with a category per part (`ring`, `desktop`, …):

```sh
log stream --style compact --level debug --predicate 'subsystem == "com.guivalenca.turnover"'
```

In zsh, `log` is a shell builtin: if that command complains, use `/usr/bin/log`.

## Common changes

**A new output format.** Add a `ConversionAction` (images in `Sources/TurnoverKit/Actions`, videos in `Sources/TurnoverKit/Video`) and a case in `OutputFormat`, which gives it its name and its `--to` value. Add the case to `OutputFormat.allCases` too: the list is written out, because `original` (a web image saved as it is) is a case that files on disk are never offered. The compiler then points at the few places that list every format: the Finder extension's menu action, the "already a PNG" reason, and, for an image format, its size estimates.

**What a drag carries.** The ring takes drags of files, and of images dragged as pictures out of a web page. `DraggedImage` (TurnoverAppCore) decides from the drag pasteboard's types, and its tests hold the types Safari and Chrome put there. To see what another app puts on a drag, log `NSPasteboard(name: .drag).types` from `DragWatcher`.

**Text people see.** It lives in each target's `Localizable.xcstrings` (TurnoverKit, TurnoverAppCore, RingModel and the app), in English for now. Counts use the catalogs' plural forms. The command's own messages are English only.

**The icon.** `swift scripts/make-icon.swift` writes the ring's shapes into `App/AppIcon.icon` and the menu bar glyph; colours, glass and the dark appearance are in `App/AppIcon.icon/icon.json`, which Icon Composer edits. `--previews <folder>` renders every appearance (it needs Xcode's Icon Composer).

## Proposing a change

1. For anything beyond a small fix, open an issue first, so the behaviour can be agreed before the code.
2. Work on a branch named after the issue, like `ticket/18-desktop-results`, with commits that say why.
3. Run `make test`, and the manual checks your change touches.
4. Open a pull request into `main` that links the issue (`Closes #18`). The template's checklist comes with it.

## Releasing

1. Set `MARKETING_VERSION` in `project.yml` and run `make project`.
2. Add the version to [CHANGELOG.md](CHANGELOG.md).
3. Go through the whole manual checklist on a build from `make install`.
4. Merge into `main`, tag it `vX.Y.Z`, and publish a GitHub release with the changelog's notes.
